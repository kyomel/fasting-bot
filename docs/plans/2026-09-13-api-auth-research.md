# API Authentication - research notes (2026-09-13)

Sources backing `plans/AUTHENTICATION_API_PLAN.md`. Collected via Exa search;
all links are official/vendor-neutral references.

## Decisions and their sources

### Opaque bearer token + server-side session (no JWT)

- OWASP Session Management Cheat Sheet: session IDs must be generated by a
  CSPRNG with **at least 128 bits of entropy**, and the session's meaning
  (user, role, expiry) lives **server-side** - the token is just a reference.
  https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html
- OWASP ASVS V7.2.3: reference tokens must be "generated using a
  cryptographically secure pseudo-random number generator (CSPRNG) and
  possess at least 128 bits of entropy". Our token is 256 bits from
  `crypto/rand` - exceeds the floor.
  https://asvs.dev/v5.0.0/V7-Session-Management/
- Revocation: ASVS V7.4.1 requires that logout "disallows any further use of
  the session" by invalidating backend state - trivial with server-side
  sessions (`revoked_at` timestamp), painful with self-contained JWT.
  This is the main reason JWT was rejected: one service, no external IdP,
  and server-side revocation is simpler and safer.

### Only the SHA-256 hash of the token is persisted

- OWASP Session Management Cheat Sheet recommends logging/storing a salted
  hash of the session ID rather than the ID itself, so a leaked store or log
  does not hand out live sessions.
  https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html
- OWASP CheatSheetSeries issue #1153 documents the accepted pattern:
  "use `session_id` as cookie and store `hash(session_id)` server-side".
  SHA-256 is sufficient because the token is already high-entropy - a slow
  password hash is unnecessary for unguessable inputs.
  https://github.com/OWASP/CheatSheetSeries/issues/1153

### bcrypt for passwords, cost 10

- OWASP Password Storage Cheat Sheet: bcrypt with "a work factor of 10 or
  more" for legacy systems (Argon2id preferred for new designs; bcrypt is
  already deployed here and remains acceptable). Note bcrypt's 72-byte input
  limit - our min-8 policy sits well under it; a future max-length rule can
  cap at 72 bytes.
  https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html
- `golang.org/x/crypto/bcrypt` implements the Provos-Mazieres adaptive hash.
  https://pkg.go.dev/golang.org/x/crypto/bcrypt

### Generic login errors + dummy bcrypt verify (anti-enumeration)

- OWASP Authentication Cheat Sheet: identical generic errors whether the
  account is missing, disabled, or the password is wrong - and it calls out
  the **timing discrepancy**: returning early on unknown username leaks
  account existence via response time. The recommended fix is exactly what
  `Login` does: run one bcrypt verification on the missing-user path
  (`dummyPasswordHash`) so both paths take ~equal time.
  https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html

### Token generation primitive

- `crypto/rand` docs: `Read` fills from the OS CSPRNG (getrandom(2) on Linux,
  arc4random_buf on macOS, ProcessPrng on Windows). Go 1.24+ also offers
  `rand.Text()`; we use `rand.Read` + base64url for explicit control of the
  256-bit size.
  https://pkg.go.dev/crypto/rand

## Transport requirement

Bearer tokens are plaintext credentials in the `Authorization` header. The
API must sit behind an HTTPS reverse proxy in production (documented in
`.env.example` and README). RFC 6750 defines the `Bearer` scheme usage.
https://datatracker.ietf.org/doc/html/rfc6750
